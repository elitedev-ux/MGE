# MGE Supabase backend

Project: `lyamovqhybstlyawnvhy`. The URL and publishable key in `client/src/backend-config.ts` identify the project but grant no write access. Optional overrides are in `.env.example`.

## Architecture

- `public.products`: catalogue fields, stock/price constraints, stable IDs, ordered display, revisions, timestamps. RLS and grants allow visitors to read only.
- `mge_private`: bcrypt password hash, SHA-256 session-token hashes, and fifteen-minute failed-login records. This schema is not exposed to the Data API; browser roles have no privileges. Its RLS deliberately has no public policies.
- `mge-admin` Edge Function: verifies the shared password and opaque eight-hour session on every admin action. Supabase supplies its service-role secret on the server. Gateway JWT verification is off because this function implements its own authentication; every action except login requires a database-backed session.
- `product-images` public bucket: public delivery, no direct client upload policy, PNG/JPEG/WebP, maximum 3,145,728 bytes. The function also verifies size and file signatures before uploading.
- Storefront reads Supabase REST; admin writes use the Edge Function. WhatsApp checkout and local bags/wishlists are unchanged. Supabase Auth accounts grant no admin rights; there is no customer registration.

Never place passwords or service-role keys in source control or `VITE_` environment variables.

## Deployment

The initial schema is in `supabase/migrations/20261024074039_mge_catalogue_backend.sql`, applied to the empty project through MCP. `supabase/seed.sql` is a non-overwriting initial import, regenerated by `node scripts/prepare-supabase-seed.mjs`. Do not overwrite owner edits with the old local catalogue. `client/src/data.ts` is retained as the import source, not the runtime catalogue.

The project now has the schema, original 76 products, password hash, and Edge Function. Existing optimized photos are distributed with the frontend; new/replacement uploads live in Supabase. Old replaced images remain available for open customer pages; maintenance can remove unreferenced uploads through the authenticated `discardPhoto` action.

Build with `npm run build`, publish `client/dist`, and configure SPA fallback to `index.html` for `/mgeadmin`, `/product/*`, and other routes. The public config already points to MGE. Frontend hosting remains a separate step. Do not expose the development server as production.

Deploy function changes from `supabase/functions/mge-admin/` using CLI or MCP with custom authentication retained. Apply schema changes through reviewed migrations. The built-in Supabase service-role environment value stays server-side.

## Password rotation

Through a trusted database maintenance connection, update `mge_private.admin_credentials.password_hash` using `extensions.crypt(new_password, extensions.gen_salt('bf',12))`, update `changed_at`, and delete existing `mge_private.admin_sessions` in one transaction. Supply the new password securely; do not save it in a migration. Keep the private schema unexposed and session RPC execution restricted to `service_role`.

Remove the printed temporary QA product ID through privileged maintenance, then call authenticated `discardPhoto` for its unreferenced photo.

- `supabase/tests/admin-security.sql`: transactional rate-limit, expiry, and privilege checks; rolls back all test state.

Security advisors report three informational `rls_enabled_no_policy` entries for the private tables. This is deliberate deny-by-default behavior. [Supabase explanation](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).
